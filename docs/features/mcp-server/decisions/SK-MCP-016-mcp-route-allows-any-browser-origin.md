# SK-MCP-016 — `/mcp` allows any browser Origin; cookies are never accepted there

- **Decision:** The authenticated MCP transport route (`/mcp`) accepts **any** browser `Origin`. CORS reflects the request origin (with `Authorization` in `Access-Control-Allow-Headers`, `Mcp-Session-Id` in `Access-Control-Expose-Headers`), answers OPTIONS preflight, and the previous Origin-allowlist rejection (returning 403 on unknown browser origins) is dropped on `/mcp` and its unauthenticated 401 responses. The load-bearing invariant that keeps this safe: **`/mcp` never authenticates via cookies** — the route reads Bearer tokens only, and a request carrying only cookies is unauthenticated. OAuth / consent endpoints (`/authorize`, `/token`, `/register`, `/.well-known/*`, `/oauth/mcp-bridge-callback`, `/oauth/mcp-authorize`) keep their current strict origin and redirect-URI validation unchanged — this decision moves nothing on the trust-decision surfaces. Supersedes the WS06-T5 note on `apps/mcp/src/index.ts` in `FEATURE.md` §Notes that adopted the Origin allowlist as a "DNS-rebinding defense per the MCP Streamable-HTTP spec."
- **Core value:** Bullet-proof, Free
- **Why:** Browser-based MCP clients are a growing category (the llama.cpp web UI, in-browser agent hosts, upcoming OpenAI/Claude web connectors) and the Origin allowlist rejected them all before auth even started — the founder was blocked connecting the llama.cpp web UI on 2026-08-18. The spec's DNS-rebinding wording targets `localhost`-bound MCP servers where an attacker page can trick a browser into resolving the server's name back to a public IP; it does not apply to a TLS remote at `mcp.nlqdb.com`. CSRF requires ambient credentials, and `/mcp` authenticates via `Authorization: Bearer` only (not cookies) — an attacker page cannot forge that header cross-origin. Token issuance is governed by OAuth PKCE + registered redirect URIs on `/authorize` and `/token`, not by `Origin` on `/mcp`. The invariant "cookies are never accepted on `/mcp`" is what keeps the CSRF reasoning true forever; it is pinned by a test (`apps/mcp/test/bearer-gate.test.ts::cookies-only is unauthenticated on /mcp`).
- **Consequence in code:** `apps/mcp/src/index.ts` bypasses the `isOriginAllowed` gate on `/mcp` and returns CORS headers reflecting the request's Origin on both success and unauthenticated 401 responses, and handles the OPTIONS preflight. `apps/mcp/test/bearer-gate.test.ts` covers: (a) OPTIONS preflight from an arbitrary browser Origin returns 204 with permissive CORS, (b) POST with an arbitrary Origin + a bogus Bearer returns 401 with the CORS headers a browser can read (so the client can start OAuth on the `WWW-Authenticate` challenge), (c) a cookies-only request to `/mcp` returns 401, and (d) OAuth endpoints still reject unknown browser Origins with 403.
- **Alternatives rejected:**
  - **Keep the allowlist, ask operators to add each new browser host to `MCP_ALLOWED_ORIGINS`.** Requires a code / config deploy for every new browser MCP client and silently breaks anonymous users trying a new host; recreates the exact blocker the founder hit today.
  - **Reflect the Origin but also allow cookies (`Access-Control-Allow-Credentials: true`).** Would re-introduce the CSRF surface the Bearer-only invariant closes. Never sent, never accepted.
  - **Loosen `.well-known/*` and `/authorize` too.** These are the trust-decision surfaces; the OAuth PKCE + redirect-URI model does the real work there. Loosening buys nothing and expands the blast radius of any future mistake.
