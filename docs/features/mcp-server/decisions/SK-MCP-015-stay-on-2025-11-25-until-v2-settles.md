# SK-MCP-015 — Serve 2025-11-25 until SDK v2 settles; never hand-roll 2026-07-28 on v1

- **Decision:** Both `SK-MCP-001` transports keep serving MCP revision **2025-11-25** on `@modelcontextprotocol/sdk` v1, and nlqdb **does not** implement 2026-07-28 features (`server/discover`, `_meta` protocol-version negotiation, `Mcp-Method`/`Mcp-Name` routing, `resultType`) by hand on top of v1. Adopting the revision happens only as the whole-stack migration in `E-08` (archived), when that worksheet's trigger fires. Until then the served revision is pinned by a test (`packages/mcp/test/protocol-revision.test.ts`), and no deprecated primitive (Roots, Sampling, Logging) may be adopted.
- **Core value:** Bullet-proof, Free
- **Why:** The 2026-07-28 revision is final, but v1 will never serve it — support landed only in the renamed v2 packages (`@modelcontextprotocol/server`), which went `latest` at 2026-07-27T23:55Z and require Node ≥ 20 plus Zod 4. On Workers the statelessness win is reachable only through `createMcpHandler`, which requires v2 *and* replaces the `McpAgent` that `SK-MCP-014`'s revocation cache lives inside (`McpAgent` is now deprecated and feature-frozen). So it is one coupled migration, not an SDK bump. Meanwhile nothing is broken: the revision's own back-compat rule has new clients fall back to `initialize`, deprecations carry a 12-month window, and the Claude Connectors Directory accepts streamable HTTP and still accepts DCR — so the queued submission is unaffected. The failure mode this guards against is the tempting middle path: partially emulating the new revision on v1 to look current, which forks the protocol layer and makes the real migration harder.
- **Consequence in code:** `packages/mcp` and `apps/mcp` stay on `@modelcontextprotocol/sdk` 1.29.0 with `zod ^3.25`. `packages/mcp/test/protocol-revision.test.ts` fails if the negotiated revision changes, if a deprecated primitive appears in `packages/mcp/src`, or if the tool catalog loses deterministic ordering / a `title` / an annotation hint. A PR adding `server/discover`, `resultType`, or `_meta` capability negotiation *without* moving to v2 fails review; the reviewer points at `E-08`.
- **Alternatives rejected:**
  - **Bump to v2 now** — a hours-old major, across a deprecated `McpAgent`, on the live connector URL, to serve a revision no client yet requires. Also breaks `engines.node >= 18` for `npx -y @nlqdb/mcp` users. `E-08` stages this instead.
  - **Hand-roll 2026-07-28 on v1** — cheap-looking and the worst outcome: a forked protocol layer to unpick during the real migration, for cosmetic currency.
  - **Bump v1 1.29.0 → 1.30.0** — pure maintenance; buys no revision support, so it is churn on two published surfaces. Fold it into `E-08` run 1 if convenient.
  - **Stateless-only on the hosted path, keep stdio on v1** — the transports would serve different revisions, violating `GLOBAL-002` behaviour parity for no gain.
