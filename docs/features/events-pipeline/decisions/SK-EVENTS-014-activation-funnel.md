# SK-EVENTS-014 — `db.*` activation events: close the anon-create → adopt funnel gap

- **Decision:** Two events instrument the top of the activation funnel. `db.created` (`dbId`, `principalId`, `anon`, `engine`, `preset`, `tableCount`, `synthetic`) is emitted by `orchestrateDbCreate` once per successful create — anonymous creates included, with `anon` derived from the `anon:` tenant prefix rather than a caller-supplied flag. `db.adopted` (`userId`, `dbId`, `replay`) is emitted from the `SK-ANON-012` adoption hook in `apps/api/src/auth.ts` when a sign-in claims an anonymous database; `replay: true` marks the idempotent re-run of an already-adopted db so a replayed hook can't inflate the conversion count. Both route to a LogSnag `activation` channel (`db.created` `notify: false`; `db.adopted` notifies only on first adoption) and, in the PostHog sink, use **`dbId` as `distinct_id`** — the same key `ask.completed` already uses — so create → ask → adopt is one joinable funnel despite server-side events having no stable person identity.
- **Core value:** Honest latency, Free, Bullet-proof
- **Why:** The product's whole activation story is "create a database without an account, ask it something, then sign in to keep it", and **none of those first two transitions emitted anything**. PostHog could see `ask.completed` but not the creates that preceded it, and nothing at all for the sign-in-to-keep step, so the two conversion rates that decide whether the anonymous-mode bet works were unmeasurable — a founder could only guess whether a weak week was a traffic problem or a create-to-ask problem. Because server-side events mint a fresh `person_id` per event, the fix has to be a *shared join key*, not a new identity system: `dbId` already threads through create, ask, and adopt, so keying `distinct_id` on it makes a PostHog funnel work with no client SDK, no identity merge, and no new sink (`SK-EVENTS-013` carries the variants automatically).
- **Consequence in code:**
  - `packages/events/src/types.ts`: `DbCreatedEvent` + `DbAdoptedEvent` join `ProductEvent`; `db` added to the domain list (`SK-EVENTS-006`). `defaultId()` keys create per-`dbId` and adopt per-(`userId`, `dbId`), so a queue redelivery or a replayed adoption hook collapses downstream (`SK-EVENTS-004`).
  - `apps/api/src/db-create/orchestrate.ts`: an optional `events` dep emits after the pkLive mint, fire-and-forget through `waitUntil` — a sink or queue fault can never fail or slow a create (`SK-EVENTS-003`). `build-deps.ts` wires the real emitter.
  - `apps/api/src/auth.ts`: the adoption hook emits `db.adopted` on `result.ok && result.dbId`.
  - `apps/events-worker/src/sinks/posthog.ts`: `distinctId()` returns `dbId` for `ask.completed | db.created | db.adopted`. `logsnag.ts`: both variants → `activation` channel.
- **Alternatives rejected:**
  - **Identify server-side events to a person.** Requires an identity-merge path and a stable anon id surviving sign-in; `dbId` is already the funnel's natural unit and needs no new machinery.
  - **Emit `db.created` from the HTTP route instead of the orchestrator.** The route isn't the only caller (presets, synthetic seeds) and would miss or double-count; the orchestrator is the one place a database actually comes into existence (`GLOBAL-021`).
  - **Reuse `user.first_query` as the activation proxy.** It fires only a few times a month and conflates "asked something" with "kept the db"; it answers neither transition.
  - **Client-side capture of the create.** Anonymous creates happen server-side and blockers eat the beacon — exactly the failure mode `SK-EVENTS-012` was created to avoid.
