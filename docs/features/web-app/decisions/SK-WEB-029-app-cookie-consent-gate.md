# SK-WEB-029 — `/app` cookie consent: PostHog gated by an opt-in prompt, chat gated by Tawk's native Consent Form

- **Decision:** The two non-essential third-party cookies on the authenticated `/app` surfaces are gated behind opt-in consent (ePrivacy Art 5(3)) by two different mechanisms:
  - **PostHog analytics (`SK-WEB-024`)** — a first-party prompt: `lib/consent.ts` holds the opt-in choice in `localStorage` (`nlqdb_consent`, `granted`/`denied`, version-prefixed) and broadcasts it on a `nlqdb:consent` window event; `ConsentBanner.astro` (Accept/Decline, mounted on each `/app` page beside `<AppAnalytics/>`) sets it. `AppAnalytics.astro` wraps its PostHog load in `whenConsentGranted(...)`, so the SDK never loads before Accept and never loads on Decline / no-choice (fail-closed). Withdrawing a prior grant reloads the page (a running SDK can't be torn down in place); a persistent "Analytics settings" affordance re-opens the prompt so withdrawal is as easy as granting.
  - **Tawk support chat (`SK-WEB-025`)** — Tawk's **own native Consent Form** (dashboard: Administration → Chat Widget → Consent Form), which blocks Tawk's cookies/localStorage until the visitor accepts an in-widget prompt. This keeps the chat bubble visible to everyone while staying compliant. It is operator configuration, not repo code — **the toggle MUST stay enabled**.
- **Core value:** Bullet-proof, Effortless UX
- **Why:** Both SDKs set their own cookies, so consent is required before they load. Marketing stays cookieless/banner-free (`GLOBAL-034`); this gate is `/app`-only. The split is deliberate: PostHog has no in-product consent surface, so it needs a first-party prompt; Tawk has one, and using it keeps the support bubble present for decliners (the entry point survives; the cookie waits for in-widget consent) instead of vanishing — a single custom banner blocking the whole Tawk load would hide the bubble on decline. The first-party session cookie is strictly necessary and never gated — declining does not sign the user out.
- **Consequence in code:** `apps/web/src/lib/consent.ts` (+ `consent.test.ts`), `components/ConsentBanner.astro`, the `whenConsentGranted` wrap in `components/AppAnalytics.astro`, `<ConsentBanner/>` mounted on each `/app` page that carries `<AppAnalytics/>`, and `nlqdb_consent` registered as a non-tool token in `data/mcp-tool-integrity.test.ts`. The Tawk half is a dashboard setting (no repo code), recorded here and in `SK-WEB-025`; user-facing disclosure lives in `privacy.astro` / `SUBPROCESSORS.md`.
- **Alternatives rejected:**
  - **One custom banner gating both Tawk + PostHog.** Blocking the whole Tawk load hides the chat bubble on decline — the support entry point vanishes. Tawk's native form keeps the bubble and is less code.
  - **No gate (functional-cookie stance).** Keeps 100% coverage but leans on a narrow, contested reading of the "strictly necessary" exemption for proactively-loaded trackers — the weaker position; consent is the one we never have to defend.
  - **Cookieless PostHog (memory-only persistence).** Avoids consent but loses the cross-session funnels/retention that are the whole reason PostHog is wired (`SK-WEB-024`).
