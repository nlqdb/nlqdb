# SK-STRG-010 — `RunState.blocked`: a walk the instrument was refused is not a walk the product failed

- **Decision:** `RunState` and `StepStatus` gain `blocked`, and the walker scores a step `blocked` — not `fail` — when the `/v1/ask` response is **428 with `challenge_required` in the body**, and only then. The verdict is derived from the steps by the pure `runOutcome(steps)` in `tools/stranger-test/src/outcome.ts`: **any `fail` anywhere outranks any `blocked`**, so a run is `blocked` only when no step failed. `WalkResult.summary` reports `passed` / `failed` / `blocked` as three separate counts; `failedStep` names a genuinely *failed* step or is `null`. The runner exits non-zero on `failed > 0` only, so a blocked-only walk exits 0. TTFV percentiles are computed over **passing runs only**. Scorecard row #21 reads `failed`; `blocked` is reported beside it and never folded in.

- **Core value:** Bullet-proof, Goal-first

- **Why:** Turnstile runs on every anonymous create ([`SK-ANON-012`](../../anonymous-mode/FEATURE.md)) and a headless Chromium on a GitHub-Actions datacenter IP is precisely the client it exists to decline, so FLOW-001 step 5 and FLOW-002/003's submit step return 428 by design from the cron — for as long as the cron runs from CI. Scoring that as `failed` pinned row #21 at a permanent `0/9`, and a metric that is always red carries no information: the [`SK-ANON-015`](../../anonymous-mode/decisions/SK-ANON-015-cross-origin-prompt-handoff.md) handoff regression — every `/solve` · `/vs` · `/agents` CTA discarding the visitor's goal — sat unnoticed inside that red for days, because 6 real product failures and 3 designed challenge rejections rendered identically. Splitting the two states is what makes the walker's silence meaningful again: after the fix, the same nine walks read `0 failed / 9 blocked`, and the next real break moves a number that was otherwise saturated. The narrow 428-**and**-`challenge_required` gate is the load-bearing half — `apps/api` mints that pair in exactly one place (the anon-create Turnstile gate) and uses 428 for nothing else, so a bare 428, a 401, a 429 or a 5xx all stay `fail`. Arming a Turnstile *test* sitekey in production to make the walker green is rejected outright: it would weaken the live bot floor to flatter an instrument.

- **Consequence in code:** `outcome.ts` holds both pure functions (`classifyAsk`, `runOutcome`) with no Playwright import, unit-tested in `test/outcome.test.ts` including the two perturbations that matter — a status-only classifier, and a `runOutcome` that lets `blocked` win — each of which turns the suite red. The three flow walkers keep a local stop-walking latch (a blocked step leaves the later steps unobservable, so they still `skip`) but no longer compute their own verdict. **What a `blocked` walk therefore does *not* assert:** FLOW-001 steps 6–8 (trace toggle, snippet copy, the `SK-ANON-012` second-ask wall) go unobserved, because the block lands at step 5. FLOW-002's blocked step 9 is its last, so steps 1–8 — including the `SK-ANON-015` handoff assertion at step 6 — are fully asserted and still turn the walk red. FLOW-003's step 9 runs regardless. So `0 failed` means "nothing the walk could see is broken", never "the flow works"; the unobserved arm needs a stranger IP, not a code change. `runOutcome([])` is `failed` for the same reason — a walk that observed nothing is not a walk that found nothing wrong. `acquisition-health.yml`'s summary reports the three counts, labels each non-passing walk `FAILED` or `BLOCKED`, and its table cell shows `blocked (n/9, 0 failed)` — one product failure among any number of blocks still renders the walk red. A new instrument limit gets a new `classifyAsk` branch and a negative test; it must never widen an existing one.

- **Alternatives rejected:**
  - **Keep scoring 428 as `failed` and read the detail string.** The status quo. It requires every reader to re-derive the split by eye from the job log, which is exactly what three consecutive `/daily` runs failed to do.
  - **Drop the challenge-blocked steps from the walk entirely** (stop asserting `/v1/ask`). Silently narrows what the canonical flows cover: a real 500 on the create path would become invisible rather than merely non-red.
  - **Score any non-200 `blocked` when the walk runs in CI** (an env-gated leniency). Green-washes every server error the walker exists to catch, and makes the verdict depend on where it ran rather than on what happened.
  - **Track `blockedStep` alongside `failedStep` in each flow.** Works for FLOW-001/002, but FLOW-003's step 9 (`/llms.txt`) runs *after* the blocked submit — a per-flow latch would let a blocked step 8 mask a failed step 9. Deriving the verdict from the steps closes that by construction.
