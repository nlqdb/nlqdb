# SK-ICP-015 — One KV put per run, not per item

- **Decision:** The weekly pipeline writes a fixed, item-count-independent number of KV keys. `runIcpScrape` dedups against a single `icp:seen` index (`{"<source>:<id>": <first-seen ms>}`, pruned to the 90-day window on every write, 90d TTL) and stores that run's new items as one `icp:items:<YYYYMMDD>` JSON array (30d TTL). `runIcpScore` accumulates across its LLM batches and stores one `icp:scored:<YYYYMMDD>` JSON array (30d TTL). `runIcpCluster` still lists the `icp:scored:` prefix, but each key now yields an array. A run with zero new items writes no seen/items key at all. Supersedes the per-item key schemas of SK-ICP-001 (`icp:seen:<source>:<id>`, `icp:item:<YYYYMMDD>:<source>:<id>`) and SK-ICP-002 (`icp:scored:<YYYYMMDD>:<source>:<id>`); every other clause of both stands.
- **Core value:** Free, Bullet-proof
- **Why:** The per-item schema cost 2 puts per new item plus 1 per scored item. A typical run stores ~260–300 new items, so a single Monday cron burned ~620 of the Workers KV free-tier **1000 puts/day** and exhausted the account quota for the whole day — [`GLOBAL-013`](../../../decisions/GLOBAL-013-free-tier-bundle-budget.md) pins the project to that tier, so a background cron must not be able to starve the product surface. Batched, the same run costs ~4 puts (seen index, items array, scored array, `icp:last_scrape_stats`) — a ~99% reduction that stays flat as sources are added. Reads drop the same way: one seen-index get replaces ~1000 per-item gets.
- **Consequence in code:** `icp-scrape.ts` gains `SEEN_INDEX_KEY` + `readSeenIndex`, marks ids in the in-memory index as it walks the item list (which also dedups within a run), prunes past-window entries before the write, and issues the two puts only when the run produced new items. `icp-score.ts` collects `IcpScoredItem[]` across batches and puts once at the end. `icp-cluster.ts`'s `readScoredItems` parses each value as an array and drops the old 50-key chunking (the window now holds ≲30 keys, so one parallel read). No migration: old-format keys are ignored and expire on their own, so the first run after deploy cold-starts dedup and may re-store items already harvested in the previous 90 days — they flow through scoring and clustering exactly like new ones, one time.
- **Alternatives rejected:** One seen-index key per source (9 puts instead of 1 for no benefit — the combined index is ~200 KB at 90 days of volume, far under KV's 25 MiB value cap); keep per-item keys and shorten the seen TTL (cuts the window, not the put count, and dedup quality is the point of the window); move raw storage to R2 now (already parked in this feature's open questions until a KV namespace nears its limits — this fix costs a fraction of that migration); a Durable Object counter to throttle puts (adds a moving part to stay inside a budget that batching removes entirely).
