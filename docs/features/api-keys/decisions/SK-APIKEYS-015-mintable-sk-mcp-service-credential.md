# SK-APIKEYS-015 — `sk_mcp_*` is dashboard-mintable and is *the* headless-MCP credential

- **Decision:** `/app/keys` mints `sk_mcp_*` alongside `sk_live_*` (`POST /v1/keys` with `{type:"sk_mcp", host, device}`, plaintext copy-once per [`SK-APIKEYS-002`](SK-APIKEYS-002-argon2id-no-plaintext.md)), and `sk_mcp_*` — not `sk_live_*` — is the credential every headless MCP path hands a user. Three properties are ratified with it:
  1. **Least privilege.** An `sk_mcp_` key is a strict subset of `sk_live_`. It may ask (including create-by-ask), list + describe its tenant's databases, and read/write agent memory. It may **not** connect a BYO database (`POST /v1/db/connect` → 403 `connect_requires_account`) and may not mint, list, or revoke keys (those routes are session-only). It carries the `(mcp_host, device_id)` claims of [`SK-APIKEYS-004`](SK-APIKEYS-004-mcp-per-host-per-device.md), so one host on one machine is the revocation and attribution unit. Per-database narrowing is deliberately **not** in scope (see the feature's open questions).
  2. **Revocation.** Individually revocable from `/app/keys` ([`SK-APIKEYS-011`](SK-APIKEYS-011-hard-revoke.md); ≤ 1 s to live MCP sessions via `SK-MCP-014`). "Sign out everywhere" does **not** revoke it — and does not revoke any minted key. Sign-out clears web sessions and CLI device refresh tokens; keys are killed by key revocation. This replaces [`SK-APIKEYS-006`](SK-APIKEYS-006-global-signout-scope.md).
  3. **Attribution.** `surfaceFromPrincipal` labels it `mcp` whatever the mint path, so headless-MCP adoption is measurable in the events pipeline.
- **Core value:** Bullet-proof, Effortless UX, Seamless auth
- **Why:** [`SK-APIKEYS-009`](SK-APIKEYS-009-sk-mcp-server-side-mint.md) made `sk_mcp_*` OAuth-mint-only, so the only key a headless user could obtain for themselves was the full-account `sk_live_*`. Two defects followed: a one-paste MCP setup handed out an over-scoped credential (it can connect BYO databases; nothing about "put this in your agent's config" implies that), and `surfaceFromPrincipal` labeled that traffic `cli`, so headless-MCP adoption was invisible. Minting a properly-scoped key from the dashboard fixes both with the narrower credential, not the wider one — the mint endpoint, the claims, the label, and the revoke path all already exist, so this is a mint affordance, not new authz. Current practice for non-human MCP workloads is exactly this: a service credential minted from an admin surface, distinct from the interactive OAuth flow (Atlassian's remote MCP server added service-account API keys over `Authorization: Bearer` for headless hosts in March 2026; the OAuth client-credentials pattern is the same shape — stable credential, no human in the loop). Guidance for headless deployments is a long-lived key with an explicit rotation story rather than a refresh-dependent token (sources checked 2026-07-28: [Atlassian Rovo MCP API-token auth](https://community.atlassian.com/forums/Atlassian-Remote-MCP-Server/Announcing-authentication-via-API-token-for-Atlassian-Rovo-MCP/ba-p/3197014), [NVIDIA NeMo MCP service-account auth](https://docs.nvidia.com/nemo/agent-toolkit/latest/components/auth/mcp-auth/mcp-service-account-auth.html), [Zylos, headless agent credential management](https://zylos.ai/research/2026-03-04-ai-agent-credential-management-headless-deployment/)). Sparing it from global sign-out is the same practice: a GitHub PAT survives signing out of github.com, because a service credential that dies when a human closes a browser is not a service credential. `SK-APIKEYS-006`'s lost-laptop case is served better than its sweep served it — `/app/keys` lists every `sk_mcp_` row with host · device · last-used and revokes one in a click, which is precise where the sweep was blanket (and which did not exist when `SK-APIKEYS-006` was written).
- **Consequence in code:** `apps/web/src/components/keys/KeysPanel.tsx`'s mint dialog offers both types; `mint-request.ts` is the pure form→`MintKeyRequest` mapping (host + device required for `sk_mcp`, caps matching the route's `MCP_HOST_MAX` / `DEVICE_ID_MAX`). `POST /v1/keys` needed no change — `type:"sk_mcp"` was already accepted, `Idempotency-Key` already dedupes (`SK-APIKEYS-013`). The `sk_live_`-only capability is pinned by `canConnectDatabase` in `apps/api/src/principal.ts`, the one place the `sk_mcp_` ⊂ `sk_live_` boundary is expressed; widening it needs an amendment here. No global-sign-out key sweep may be added — a PR that revokes minted keys on sign-out contradicts this decision.
- **Alternatives rejected:** Keep documenting `sk_live_` for headless MCP — ships an over-scoped credential as the happy path, and hides MCP adoption behind the `cli` label. Add a fourth key type for headless MCP — `SK-APIKEYS-001` caps the type count at three, and `sk_mcp_` already means exactly this. Keep `SK-APIKEYS-006`'s sweep but exempt dashboard-minted rows — needs a provenance column on `api_keys` to distinguish two mint paths that produce identical rows, for a sign-out endpoint that does not exist yet; a rule the schema cannot express is a trap.
