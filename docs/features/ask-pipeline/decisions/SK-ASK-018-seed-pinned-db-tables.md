# SK-ASK-018 — Seed `routeAsk` recentTables from the pinned DB's `schema_text` on every pinned ask

- **Decision:** When `/v1/ask` arrives with a pinned `dbId`, the handler folds a `RecentTable` per `CREATE TABLE` in the pinned DB's `schema_text` into the `recentTables` fed to `routeAsk` — seed tables first so the pinned DB wins a table-name tie, MRU deduped by `(dbId, table)`. The read is memoized per request (`memoResolveDb`), shared with the orchestrator's exec read (one D1 point-read, not two) and run in parallel with the MRU/list reads so it never sits on the critical path.
- **Core value:** Effortless UX, Goal-first, Fast
- **Why:** The original gate (`recentTables.length === 0`) seeded only on a cold MRU. A user with tables from *other* DBs in their MRU asking a read against a freshly-connected pinned DB (`"how many campaigns…"`) fell through to routeAsk's LLM, which applied its "unknown table → create" bias and dead-ended on the create/query clarify — the reported bug. The pinned DB's tables are always the relevant context for a pinned ask, so the seed is now unconditional; memoizing keeps it free (the orchestrator already resolved the same row).
- **Consequence in code:** `index.ts` builds one `memoResolveDb(c.env.DB)` per request, feeds `mergeSeededTables(seedFromPinnedDb(db), mru)`, and passes the same memo to `buildAskDeps`. Seed rows stamp `touchedAt = 0` so any real touch outranks them. Best-effort: a D1 throw leaves the MRU untouched.
- **Alternatives rejected:** Gate on cold MRU only (prior rule) — misses the common multi-DB case. A second un-memoized read — doubles the pinned-path read for no gain. Migrate the anon MRU on adoption — a KV op on sign-in for a rare payoff.
