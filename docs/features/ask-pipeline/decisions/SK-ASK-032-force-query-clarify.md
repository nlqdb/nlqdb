# SK-ASK-032 — `forceQuery` resolves the create/query clarify without re-classifying — a guided turn, not a loop

- **Decision:** The `SK-ASK-014` create/query clarify (`clarification: "create_or_query_pinned"`) is resolved by re-sending the goal with `forceQuery: true` alongside the pinned `dbId`. On that request `routeAsk` is **skipped entirely** — the route is synthesized as `kind=query` against the pin (`reason: "forced_query"` on the span). `forceQuery` is honoured only with a pinned `dbId` (a no-op otherwise) and parsed truthy-only (`=== true`), the same defensive coercion as `confirm`.
- **Core value:** Effortless UX, Bullet-proof, Fast
- **Why:** Re-sending the identical goal + pin re-ran the identical classifier, which deterministically re-derived `kind=create` and re-returned the same clarify — a dead-end loop the user hit by clicking "Query *<db>*" repeatedly (each click also paid a wasted ~150 ms route LLM hop). The clarify's chip carried no signal that the user had *decided*; `forceQuery` is that signal, and skipping `routeAsk` makes the confirmation instant and loop-proof. This is `GLOBAL-040`'s "a clarify is a guided turn, not a dead-end" applied to the create/query clarify.
- **Consequence in code:** `AskBody` / SDK `AskRequest` gain `forceQuery?: boolean`; `index.ts` computes `forceQuery = body.forceQuery === true && Boolean(body.dbId)` and short-circuits the `routePromise` to a synthesized `kind=query` output; `ChatPanel.acceptClarifyQuery` sends it; the CLI exposes `--force-query` and points its clarify hint at it. `routeAsk`'s `RouteAskReason` gains `"forced_query"`. Pairs with the widened `SK-ASK-018`: the seed stops most read-shaped goals from misclassifying in the *first* place; `forceQuery` guarantees the *confirmation* can never loop.
- **Capability parity (`GLOBAL-003`):** SDK + web + CLI ship it. MCP/elements deliberately do **not** — the create/query clarify is an interactive resolution, and an MCP agent benefits from the `SK-ASK-018` seed automatically (it applies to every `/v1/ask`); a `forceQuery` knob on the agent tool surface for a rare, non-interactive case is not worth the schema growth. Tracked, not wired.
- **Alternatives rejected:** Override `kind` *after* running `routeAsk` — still pays the wasted LLM hop. A per-goal heuristic to stop the misclassification — `SK-ASK-018` covers the common case, but no heuristic can *guarantee* a confirmation never loops; only an explicit intent signal can. Retype-to-rephrase (the old dead-end) — the exact UX the bug report called "annoying / unprofessional".
