# SK-ANON-016 — `/app/new/` bypasses the anon path entirely for a signed-in visitor; an unrecoverable Turnstile challenge hands off to sign-in instead of dead-ending

- **Decision:** `CreateForm.tsx` takes a new `allowAuthedCreate` prop, set only by `apps/web/src/pages/app/new.astro` (never `Hero.astro` or `agents/index.astro`). When set, `submit()` calls `fetchSession()` (`lib/session.ts`, the existing Better Auth session probe) at click time; if a session exists, `postAskCreate(apiBase, goal, { authed: true })` sends the request with `credentials: "include"` and no `Authorization` header — no anon bearer at all. When Turnstile can't be solved for a signed-out visitor (the retry seam in `submit()` gets a null token, or the resolved token still comes back `challenge_required`), the prompt is stashed to `nlqdb_pending` and the visitor is redirected to `/auth/sign-in/?return_to=/app/` — the same hand-off `SK-ANON-010`'s `auth_required` envelope drives, just without a server-supplied `signInUrl` (the 428 envelope carries none).
- **Core value:** Bullet-proof, Effortless UX, Seamless auth
- **Why:** `/app/new/` is CLAUDE.md P6's "world-class customer journey" surface for the *signed-in* create path, not only the anon one — `SK-ANON-001`'s `credentials: "omit"` was written for the marketing hero, where forcing anon is the point (SK-ANON-012's device cap must fire even for a visitor signed in from another tab). Reused verbatim on `/app/new/`, the same rule meant a signed-in user opening the app's own "create" page got funneled through the anon Turnstile/device-cap gates regardless of their session — reported as "the page is broken, same error signed in or out" when Turnstile itself was also failing in production. Two independent fixes close this: (1) a signed-in visitor never needs the anon path at all — `requirePrincipal` (`SK-ANON-008`) already resolves a cookie session as `principal.kind === "user"`, which skips every anon gate server-side, so riding the cookie on `/app/new/` is strictly safe and always works regardless of Turnstile's state; (2) a signed-out visitor whose challenge is unsolvable has no code path back to a working create — the old UI left them on a raw "Complete the browser challenge to continue" error with no next action, which is exactly the dead-end CLAUDE.md P6 rules out. Handing that visitor to sign-in reuses the already-seamless `SK-ANON-010`/`SK-ANON-011` prompt-preservation arc instead of inventing a new one.
- **Consequence in code:** `apps/web/src/lib/api.ts`'s `postAskCreate` takes `options.authed?: boolean`; `true` swaps `credentials: "omit"` → `"include"` and drops the anon-bearer header. `CreateForm.tsx` re-checks `fetchSession()` at submit time (not just on mount) so a session that resolves between page load and click is never missed; the `signedIn` state only drives the lede copy. The `/v1/ask` server-side dispatch needs no change — `runCreatePath`'s classifier/create branch already treats `principal.kind === "user"` with no `dbId` as the create path (existing "All databases" behavior in the authed chat), so an authed visitor with existing DBs gets the same create-vs-query classification they'd get typing the same goal in `ChatPanel`. The Hero and `/agents/` call sites don't pass `allowAuthedCreate`, so their anon-only contract (`SK-ANON-001`) is byte-for-byte unchanged.
- **Alternatives rejected:**
  - Leave `/app/new/` anon-only and just fix Turnstile — doesn't address the reported "signed-in users see the same error" complaint, and re-couples every future Turnstile misconfiguration to a hard outage for signed-in users on their own app's create page.
  - Server-side force a `kind=create` classifier override for authed `/app/new/` calls — a larger, separate API-contract change (new `AskBody` field, SDK/CLI/MCP surface per CLAUDE.md §8.6) unrelated to this bug; the existing "All databases" classifier behavior is already the accepted UX for a no-`dbId` authed create.
  - Redirect every visitor (signed in or not) to sign-in on any Turnstile failure — would force a re-auth loop for an already-signed-in visitor, which is exactly what the user's bug report ruled out ("a logged in user must work").
